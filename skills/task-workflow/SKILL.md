# 과제 진행 순서

이 과제의 요구사항은 README에 다 적혀 있지 않고, 사용자가 업무 담당자에게 물어서 확정한다.
너는 규칙을 추측으로 정하지 않는다. 애매한 점은 사용자가 담당자에게 물을 질문으로 바꿔 준다.

## 1. 탐색 (코드 수정 금지)

- README, 데이터 폴더, 기존 코드, 테스트를 읽고 파일별 컬럼과 행 수를 표로 정리한다.
- `data-quirks-check` 스킬의 점검표로 데이터의 이상한 점을 찾는다.
- 기존 테스트를 실행해 기준선(통과·실패 수)을 보고한다.
- 기존 코드가 어떤 규칙을 가정하고 있는지 정리한다. 통과하는 테스트도 틀린 규칙을 굳히고 있을 수 있다.
- 끝에 "담당자에게 물을 질문"을 주제별로 3~5개씩 묶어 낸다: 목적·기준 시점·우선순위 / 용어와 규칙의 정의 / 데이터 / 출력 파일과 받는 쪽 제약.

## 2. 정의 먼저

- 사용자가 담당자의 답을 알려 주면 PLAN 문서에 정의표를 만든다: 항목 | 정의 | 근거(담당자 확인·문서·추측) | 테스트로 고정할 예.
- 이후 모든 구현의 기준은 이 정의표다. 기존 코드·테스트·문서가 정의표와 다르면 차이를 먼저 알린다.

## 3. 구현 (한 번에 한 단위)

- 한 요청에 함수 하나와 그 테스트만 만든다.
- 기존 테스트가 정의표와 다른 규칙을 굳히고 있으면 바로 고치지 말고 알린다. 사용자가 승인하면 고치고, 바꾼 이유를 테스트 설명에 한 줄 남긴다.
- 변경할 때마다 보고한다: 테스트 실행 결과, 쉬운 말 3줄 요약, 정의표의 어느 줄을 구현했는지.

## 4. 검증

- 핵심 숫자는 다른 계산 경로나 손 검산과 대조한다.
- 예외 사례(경계값, 동명이인, 기간 경계, 상태 변경, 중복)를 사람·레코드 단위 표로 보여 준다.
- 화면, API, 내보내는 파일로 개인정보가 나가는 경로가 없는지 확인한다.

## 5. 기록

- 결정할 때마다 COLLAB_LOG 문서에 시각, 결정, 근거(담당자 확인·데이터·추측), 검증 결과를 추가한다.
- 하지 않은 검증을 한 것처럼 쓰지 않는다. 사실과 추측을 구분한다.

## 하지 말 것

- 사용자 승인 없이 파일 삭제, `git reset --hard`, 대량 재작성.
- 서버처럼 계속 실행되는 명령을 대화 안에서 실행하기. 실행 명령만 알려 준다.
- 개인정보 원문을 출력하기.
